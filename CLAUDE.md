# nightfall-toolkit

A CLI (+ GUI) that packages Chromebook Linux hardware-enablement fixes as self-contained, detection-gated units — camera (IPU3), display/rotation, audio, EC/buttons, fingerprint, Waydroid, zram. Built and tested on exactly one machine: the Google Pixel Slate (Nocturne). Every fix is hardware-detected, but detection is imperfect on other hardware, and the README is explicit about that.

**A bad interaction can hard-lock the machine with no panic and nothing logged** — this happened three times during IPU3 camera work. Treat every `apply` as genuinely risky, not routine.

## This is one of three related but separate Slate projects
- **This repo** — userspace hardware-fix tool, runs on the daily-driver OS.
- **[BobZKernel](https://github.com/thewraith420/BobZKernel)**, `pixel-slate` branch — the actual installed kernel + patches. `picker-kernel` branch — a stripped-down kernel for the touch boot picker below, being replaced by the **nightfall-kernel** (release `v7.2.7-nightfall`, 2026-09-23, any x86-64 PC). `nightfall apply` fetches it: bare `vmlinuz-<rel>-nightfall` asset, verified against the release's `SHA256SUMS`; the old `*-picker` tarball is only a fallback.
- **[nightfall-boot-manager](https://github.com/thewraith420/nightfall-boot-manager)** (renamed from `nocturne-boot-picker` on 2026-09-09) — TWRP-style touch `kexec` boot manager: boots kernels, edits and remembers their command lines, installs and removes kernels, backs up and restores the system, and carries a repair menu. Installed by this repo's `nightfall` fix, and it is the Slate's default GRUB entry.

They overlap more than they look like they should — see "Non-obvious overlaps" below before assuming something here is unrelated to those repos.

## Design pattern per fix
`fixes/<id>/fix.yaml` (metadata/risk/category/description) + up to four scripts:
- `detect.sh` — 0 = problem present, 1 = not needed, 2 = can't tell
- `verify.sh` — 0 = our fix is in place and working, **3 = desired state holds but something ELSE achieved it** (not "our fix"). This exists because of a real incident: the IPU3 IOMMU fix's `verify` saw a safe `identity` domain on a stock kernel — mainline's own VT-d quirk did it, no bootloader parameter was ever added — and would have wrongly reported "applied." Keeping `detect`/`verify` conceptually separate ("problem exists" vs "our fix is installed") is deliberate, not incidental.
- `apply.sh` / `revert.sh`
- Convention: `SUDO="${FIXER_SUDO:-sudo}"`, never bare `sudo`. Under the GUI this
  resolves to `pkexec` (polkit → fingerprint); in a terminal, plain `sudo`.
- **Batch root work into one `$SUDO`.** pkexec's action is `auth_admin`, not
  `auth_admin_keep`: no credential cache, so every `$SUDO` is another
  authentication prompt. One since-removed DKMS fix fired nine, spread across a
  minutes-long build. Use `$SUDO bash -s -- "$A" "$B" <<'ROOT'` and do the
  whole privileged sequence inside it.

## GUI: home is Nightfall, not a fix list (2026-09-18 reorg)
Top to bottom on the root page: **Machine Specs** (renamed from "This machine"), a single **Hardware fixes** row (carries the count of anything needing attention, whichever category), **GRUB** — then, one heading size larger since everything below it belongs to it, **Install Nightfall** (the two `boot` fixes: `nightfall`, `nightfall-default`), **Nightfall settings** (menu timeout, starting rotation, auto-rotate, boot screens on/off + minimum time in quarter-second steps), **Kernels**, **Backups**. Window title and desktop entry both say "Nightfall Boot Manager — Chromebook Fixer"; only the group heading above the two install-related fixes says "Install Nightfall". `bin/chromebook-fixer-gui`'s `_build_root` docstring has the full reasoning.

**Kernels and Backups are view/manage only — taking, restoring and installing-from-initramfs stay in Nightfall.** Both `lib/kernels.sh` and `lib/nightfall-backups.sh` are deliberately narrower than their Nightfall-side counterparts: Nightfall does the risky half of each job from its own environment, with the real root mounted read-only (a backup of a running system would catch it mid-write; a restore would be overwriting the system performing it). What runs from here is genuinely safe on a live system and is the part that is otherwise a reboot into the touch UI just to check something:
- `kernels.sh`: list every installed kernel (owner - apt package or `-`, size, running/default flags, orphaned `/lib/modules` trees with no kernel left), remove one (apt-owned kernels go out through apt; unowned ones get exactly their own files deleted, then `update-grub`; refuses the running kernel and the last one), set/clear Nightfall's default (`/boot/nightfall-default`), and **install** one from a BobZKernel portable-installer tarball (`boot/vmlinuz-<release>` + `lib/modules/<release>/`, extracted by exact member name after a path-traversal check and a free-space check — never a blanket tar extraction). Nightfall's own `install-kernel.sh` installs the *same* tarball format, just via chroot from initramfs; there is no separate "Nightfall-style" tarball, a wrong claim that briefly existed in a code comment and was corrected (`7c2c8bc`). **"Installed by hand" for an unowned kernel was dropped from every surface (2026-10-02)** — it was a guess from "no dpkg owner" alone, and wrong for `7.2.8-BobZKernel-pixel-slate`, which the fixer itself had installed. The packaged/unowned split is still used internally (it is what decides apt purge vs. direct file removal in `cmd_remove`), just never presented as a claim about install method; the owner column/subtitle says the real package name when there is one, and nothing (CLI: `-`) when there is not.
- `nightfall-backups.sh`: list every backup on any mounted drive (Nightfall's own layout, `<drive>/nocturne-backups/<name>.tar` + `<name>.info`), including ones with no sidecar — a run Nightfall's own list hides because it cannot be restored from, but which is usually the biggest thing on the drive and exactly what you want to delete when space runs out — and delete one.
- Tests across `tests/test-nightfall-boot-safety.sh`, `test-nightfall-backups.sh`, `test-kernels.sh`, `test-nightfall-detect.sh`, `test-nightfall-apply-deps.sh` and `test-updates.sh`, all in CI (`.github/workflows/tests.yml`), fixture-only, no privilege and no real drive needed.

**Installed desktop entry does not follow `git pull`.** `~/.local/share/applications/org.chromebookfixer.Gui.desktop` is a *copy*, made by `install.sh`; editing `share/applications/org.chromebookfixer.Gui.desktop` in the checkout and pulling on the Slate changes nothing the app drawer reads until `install.sh` is re-run (idempotent, safe to re-run any time — it just re-symlinks the binaries and re-copies the desktop entry and icon). Even then, GNOME Shell on Wayland (confirmed the Slate's session: `XDG_CURRENT_DESKTOP=ubuntu:GNOME`, `XDG_SESSION_TYPE=wayland`) caches the app grid and has no live-reload trick — X11's "Alt+F2, r" restart does not exist under Wayland. A log out/in (or reboot) is the actual fix. Cost real time working this out on 2026-09-18; do not re-diagnose it from scratch next time a GUI rename "doesn't show up".

### Nightfall is no longer Slate-only (2026-09-23)
`nightfall` and `nightfall-default` have no `applies_to`: any PC with GRUB is offered them, because the nightfall kernel is a generic x86-64-v2 build. `detect.sh` no longer requires a touchscreen (it changes the row's wording — keyboard and mouse — not whether Apply exists; a Lenovo LOQ with none was what exposed the old rule hiding the button). The real gate is the CPU: `lib/cpu-level.sh` (`cpu_x86_64_v2_missing`, `FIXER_CPUINFO` override for tests) is checked by **both** `detect.sh` and `apply.sh`, since apply is reachable without detect via `--force`; below v2 the kernel dies at its first unsupported instruction with no console, so it is refused before anything is installed. Tested on the Slate and the LOQ only; the README and the row say so. The hardware fixes are unchanged and still Chromebook/board-matched.

**Debian does not put `/usr/sbin` or `/sbin` on a user's PATH** (Ubuntu and Mint do) — the reason `nightfall` applied fine on the Slate and the stick and failed on the Debian 13 LOQ: `kexec`/`e2fsck`/`efibootmgr` were installed but `command -v` (this script's package checks, and Nightfall's `build-initramfs.sh`) could not see them, so it asked apt for packages already present and then died with "kexec not found". `apply.sh` now appends `/usr/local/sbin:/usr/sbin:/sbin` to PATH (`NF_SBIN_DIRS` overrides it for tests) and runs its apt installs with `DEBIAN_FRONTEND=noninteractive` (kexec-tools asks a debconf question). Any other fix script that `command -v`s a sbin tool has the same latent bug on Debian.

### Updater (2026-09-23)
`chromebook-fixer update [fixer|nightfall|all]`, backed by `lib/updates.sh`; the GUI runs `update --check --porcelain` once at launch (own thread, network-bounded) and shows an **Updates** group only when something is behind. Both git checkouts are **fast-forward only** and refuse on local changes / unpushed commits — deliberate, because both machines commit to these repos. `update nightfall` = pull the Nightfall checkout, then the `nightfall` fix's own `apply.sh` with `FIXER_NIGHTFALL_UPDATE=1`: skips "reuse the installed kernel", fetches the newest release, rebuilds the UI, and — in the same single root step as the install — keeps the replaced `/boot/nightfall/{vmlinuz,initramfs.img}` as a matched `*.previous` pair (only when the kernel differs, so a same-kernel reinstall never overwrites a good rollback). The kernel comparison uses `sort -V`, and a kernel newer than the published release counts as current — the Slate runs one built ahead of its release. `apply.sh` fetches, in order: the kernel-only `*-nightfall-kernel.tar.gz` (deliberately not an installer, so Kernels > Install rejects it), the bare `vmlinuz-*-nightfall`, then the old `*picker*` tarball; every one is checked against the release's `SHA256SUMS`.

### Cleanup pass coordinated by the Slate session (2026-09-30)
Bob put the Slate session in charge of coordinating cross-session cleanup once a bug is fixed at the right layer. Two items landed here:
- **`ec-buttons-poll` is now firmware-aware.** `lib/ec-buttons.sh irq-live` (and a duplicated-on-purpose copy in the daemon's own `kernel_already_handles`, since the daemon is not reinstalled when firmware changes) detects SlateFirmware's patch 0001b by counting `chromeos-ec` lines in `/proc/interrupts` — one is always the FPMCU's, a second means the main EC gained its own interrupt. `detect.sh` and the daemon both stand down on it (gated on `cros_ec_keyb` being bound too — a working EC interrupt does nothing if GOOG0007 is still hidden). This isn't just avoiding redundant work: the poller injects its own synthetic key through a second uinput device, so running it alongside working native delivery double-fires every press. See overlap #1 above and `kernel/README.md`.
- **`panel-brightness-aux` no longer refuses to install on a DPCD-capable kernel.** Its install-time probe was the pre-dc5a29d one-shot version (can be fooled by a desktop's automatic brightness) and blocked install on dual-boot systems that need it on some kernels but not others. Install now always proceeds; the daemon's own per-startup probe (the dc5a29d fix) decides, and stands idle rather than fight the kernel for the same registers. Type=simple + Restart=on-failure means a clean "stand down, exit 0" reads identically to a crash to systemd, so both apply.sh's post-install check and verify.sh now ask the daemon's own `--why` (unprivileged — it falls back to a backlight-range heuristic without root, so this never adds a sudo prompt to a background status sweep) to tell the two apart; verify.sh reports standing-down as exit 3 ("nothing for this fix to do"), not broken.
- Both fixes' `detect.sh` scripts gained the same overridable-sysfs-path treatment every other `detect.sh` here already had (`DMI_SYS_VENDOR`, `DRM_DP_AUX_DIR`, etc.) — they predated that convention and could not be fixture-tested at all before this.
- **`/proc/cmdline` can go unreadable while the machine is running.** Mode 0440, owned by one of Android's uids, observed by the Slate session to start the moment Waydroid's container runs — not proven to be causal yet (their own confirming test, a reboot, is still pending), but real: it broke `fixes/audio-avs-dsp/detect.sh`, which read `/proc/cmdline` with a bare `grep -qs ... && exit 1` that fails silently on EACCES, so an already-applied cmdline fix would misreport as still needed (fixed: checks readability first, "cannot tell" (2) on failure, modprobe.d checked first since it needs no cmdline read at all). `lib/kernel-cmdline.sh` and `lib/nightfall-cmdline-check.sh` already handled this correctly (the pattern every reader should follow: `[ -r ... ] || <cannot tell>`, never let a failed read collapse into "absent"); `panel-brightness-dpcd`, `ipu3-imgu-iommu`'s detect and verify, and `nightfall/apply.sh` (transitively, via `nightfall-cmdline-check.sh`) were already fine. **The actual fix is containment, in `waydroid-lxc-hook`** (now two unrelated bugs sharing one fix id and one backup, since the Slate session's call was that this is the right layer): a `lxc.mount.entry` bind-mounts a private snapshot of the host's cmdline over the container's own `proc/cmdline`, refreshed on every apply, so Android's container never touches the real file regardless of why it does what it does. Hardening every host-side reader is the fallback for machines not yet carrying this, not a substitute for it.

  **This bind must be read-write, not read-only — a real regression, proven on hardware 2026-10-01.** The first version (`c6f3110`) bound it `,ro,`; applied on the Slate, it killed Waydroid outright. Android's first-stage init does a *fatal* `CHECKCALL chmod("/proc/cmdline", 0440)` during boot — with a read-only bind that chmod gets `EROFS`, init aborts (`InitFatalReboot`, `SIGABRT`), and the container never comes up. Dropping `,ro,` fixed it: Android boots fully, and its chmod+chown land on the *snapshot* file (which ends up `root:1001 0440`, exactly what used to leak to the host) rather than the real `/proc/cmdline` — direct, hardware-confirmed proof the containment itself works. Also fixed in the same pass: a config still carrying the old `,ro,` line is now recognized by `detect`/`verify`/`apply` as **broken, not applied** (it used to read as a healthy install while actually being a container that cannot boot) and `apply` migrates it in place rather than stacking a second `lxc.mount.entry`; and `apply.sh` was restructured around a single `$SUDO bash -s` (per the standing convention) since the original cost up to 6–8 separate pkexec prompts per run.
- **Seven `detect.sh` scripts died outright under `set -u` when run by hand** (`FIXER_REPO` unset — normally set by `Fix.run()`): `camera-orientation`, `ec-buttons-poll`, `ipu3-vcm-focus`, `ipu3-camera`, `panel-brightness-dpcd`, `ipu3-imgu-grableak`, `ipu3-imgu-iommu`. The crash's own exit code (1) reads as "not needed" — a quiet wrong answer. All seven now default `FIXER_REPO` from their own script path, matching `fixes/nightfall/detect.sh`'s existing pattern.
- **Held, not acted on, pending other sessions:** `panel-brightness-dpcd` (the `i915.enable_dpcd_backlight=2` token) may be obsolete on current firmware+BobZ 7.2.x, but the stock-kernel case is an open measurement BobZKernel/SlateFirmware are still running — do not change it until that comes back. `hid_google_hammer`'s module blacklist being load-bearing on generic 7.0.0-31 (removing it leaves the panel dark) needs documenting once BobZKernel confirms why 7.2.6 doesn't have the same problem — exact wording and version range intentionally not guessed at here yet.

### Per-kernel cmdline editing and orphan-module purging (2026-10-02)
Bob/Slate-Session asked for the fixer to edit Nightfall's per-kernel `/boot/nightfall-cmdline` overrides from the CLI and GUI, not just Nightfall's own touch UI. The file's contract was confirmed with the `nightfall-boot-manager` session first, against their actual source (not assumed) — the facts worth remembering, since getting any of them wrong silently breaks Nightfall's own boot:
- **No fixed path convention for the key.** It must be an EXACT STRING MATCH against column 2 of grub.cfg's own `linux` directive for that kernel — `apply-cmdline.sh` does a plain `$2 in want`, zero normalization. Same-partition `/boot` → typically `/boot/vmlinuz-<release>`; a genuinely separate `/boot` → typically a bare `/vmlinuz-<release>`, because GRUB's own "root" for that entry IS the boot partition. **Never reconstruct this from the release string** — `cmd_cmdline`'s root block reads it from `grub.cfg` itself (same `awk` pattern `cmd_default` already used for its own marker), falling back to the computed `grub_path()` guess only when grub.cfg has not picked the kernel up yet.
- A missing line = no override, full stop — no separate fallback value, the row just passes through grub.cfg's own entry untouched.
- Comments (`^[ \t]*#`) and blank lines are skipped; **duplicate keys: the LAST line wins**; an empty value after the tab is never an override (same as no line) — to clear one, delete the line, never write an empty value. All of `lib/kernels.sh`'s own reads/writes (`cmdline_for`, `cmdline_orphans`, `cmd_cmdline`'s root block) match by the stored key's own `vmlinuz-<release>` *suffix* rather than requiring an exact precomputed key, since grub.cfg may already be stale (regenerated, or not yet) by the time a removal or a set runs — the file's own existing keys are the only reliable source at that point.
- No locking concern: Nightfall only reads this pre-boot in its own initramfs, which cannot overlap with the fixer running on a live, normally-booted OS.
- Orphan detection (`cmdline_orphans`, surfaced in `kernels`/`list`) checks each stored key as a path, directly and then substituting `$BOOT` for a leading `/boot/` or bare `/` prefix — not a hardcoded literal `/boot`, so it works against `FIXER_BOOT_DIR` overrides in tests as well as the real `/boot`.

CLI: `kernels --cmdline <release> [--set <cmdline>|--reset]`; the unprivileged fast path answers instantly when an override is already saved (the file is `0644`, same as `NF_DEFAULT_FILE`) and only escalates to read `grub.cfg` (`0600`) when it has to. GUI: a **Cmdline…** button per kernel row opens a dialog with a wrapping multi-line field (a real cmdline is long enough that a single-line `Gtk.Entry` just scrolls, hiding `root=` off the left edge — seen on the Slate) and three responses, **Cancel** / **Clear Saved** / **Save** — Clear Saved lives in the dialog, not a separate row button, and is disabled when there is no override to clear. Guard rails on `--set`: refuses empty, refuses no `root=`, refuses a literal tab (the save format is tab-delimited). **No guard against dropping `module_blacklist=hid_google_hammer`** — deliberately removed (Bob, 2026-10-02, after trying a `--force`-gated refusal first): the override only affects boots through Nightfall, and GRUB's own entries still boot generic with the blacklist regardless, so a bad value here is recoverable without a confirmation step in the way. `kernels --remove` (every path: packaged, hand-installed, and leftover-module-only) prunes the matching line in the same single `$SUDO bash -s` call, backing the file up first; a cmdline-only orphan (no vmlinuz, no modules, no dpkg entry — just a dangling line, the live case on the Slate: `7.2.3-BobZKernel-pixel-slate`) is also a valid target for both `kernels --remove <release>` and `kernels --cmdline <release> --reset`, with no boot guard beyond refusing the running kernel, since nothing boots from it. Orphan rows (cmdline overrides and rc/module leftovers alike) carry their own Remove button in the GUI and are removable from the CLI the same way — a `kind == "cmdline"` row's column 1 is the stored *key* (a path), not a release string, so both the GUI and the CLI wrapper's own `--remove` matching derive the release from it (`split("vmlinuz-", 1)[-1]`) before calling `lib/kernels.sh`, which always wants the bare release.

Landed in the same pass, independent of the above: `lib/kernels.sh`'s orphan-module removal (`rc_packages_for`) now checks whether dpkg still owns a leftover `/lib/modules/<release>` tree in its `rc` state ("removed, config-files remain" — `apt remove` without `--purge`, confirmed real: Software Updater left `linux-modules-7.0.0-31-generic` exactly like this, 2026-10-02) and purges through apt instead of `rm -rf`-ing it by hand, which would leave dpkg's own database still claiming the package. `cmd_list` and the GUI's kernel rows both say "removed but not purged by apt" and name the owner when this applies.

154 tests total in `tests/test-kernels.sh` (up from 71), covering the cmdline format, the (now much smaller) guard rails, both path conventions, orphan detection, cmdline-only-orphan removal, every removal path, and the owner column no longer guessing an install method, all mutation-checked.

A second real-hardware round on `rc_only_releases()` (Slate session, 2026-10-02) found it was overbroad: the first version queried every rc-state `linux-*` package and stripped a fixed list of known prefixes (`image`, `headers`, `modules`, ...) to recover the release - which doesn't cover every companion package Ubuntu ships (`linux-main-modules-zfs-<release>`, `linux-signatures-nvidia-<release>`, etc.), so an unrecognised one had its *whole package name* treated as if it were itself a release, reported as a bogus duplicate orphan next to the real one. Fixed by anchoring on `linux-image-<release>` (optionally `linux-image-unsigned-<release>`) specifically, rather than trying to recognise every companion prefix: it is the one package that actually *defines* a kernel release existing, so once found, `rc_packages_for(release)`'s own substring match already sweeps up every companion package for it (ZFS modules included) without needing to recognise their names at all. Trade-off accepted deliberately: a release orphaned only in its companion packages, with `linux-image-` itself already purged, is now missed rather than guessed at - under-reporting a rare case beats offering a bogus "release" someone could point `remove` at. Also fixed in the same pass: a cosmetic double space before "still owns it" in both orphan messages, from `tr '\n' ' '` leaving a trailing separator that collided with the literal space already in the format string - `echo $var` alone (word-splitting does the join) has no such tail.

**Machine Specs' Model line showed a vendor-internal SKU code instead of a recognisable name (2026-10-02).** On the LOQ, `Machine.describe()` (`lib/registry.py`) read `LENOVO 82XV` - DMI `product_name`, a model code nobody recognizes - while GNOME's own About panel, reading DMI `product_family` instead, showed `Lenovo LOQ 15IRH8` for the identical machine; Bob's reaction was "what's with the model". `describe()` now prefers `product_family` when it is set and differs from `product_name` (`LENOVO LOQ 15IRH8 (82XV) (board ...)`), falling back to the old bare format - unchanged, byte for byte - when it is blank or identical, which is the common case on a Chromebook. **`Machine.product` (the field `Fix.matches()` keys `applies_to: {product: "..."}` on, e.g. `product: "nocturne"`) is untouched** - this is a new, separate, display-only field, not a change to what already-matching regexes compare against. `tests/test-registry.py`, new - the first Python-level test in this repo, since `Machine` is a plain frozen dataclass with no fixtures to build.

Two follow-ups from the Slate session's hardware check (2026-10-02), both landed:
- **Cosmetic:** an orphan cmdline-override row in `cmd_list`'s human-readable output used a blank first column (matching how a kernel row's own *flags* continuation line is written), so it visually read as belonging to whichever kernel printed immediately before it rather than being its own row. Fixed by putting the stale key in column 1, same as orphan module rows already did.
- **Real gap:** `rc_packages_for()` (dpkg's `rc` state - `apt remove` without `--purge`) was only ever consulted for a release `orphan_modules()` had already found a `/lib/modules/<release>` directory for. A release with dpkg entries in `rc` state but NO files left on disk at all (the module directory deleted by hand after the kernel itself was already gone - seen live on the Slate) was invisible to both `list` and `remove`. New `rc_only_releases()` queries dpkg directly (`linux-*`, filtered to `rc` state, release recovered by stripping known `linux-{image,headers,modules,...}-` prefixes, de-duplicated) for releases with neither a `vmlinuz` nor a modules directory, and `cmd_remove`'s orphan gate now accepts `rc_packages_for` being non-empty as a valid removal target on its own, not just an existing directory.

### 2026-10-03 to 10-05: updater, i915 guard, fingerprint install, progress window, rename
- **The updater compares the installed Nightfall build with the checkout, not just the checkout with origin.** Commits made locally and not yet pushed used to read "up to date" while `/boot/nightfall` was over a week stale (real, on this PC). `fixes/nightfall/apply.sh` now writes the nightfall-boot-manager checkout's HEAD to `/boot/nightfall/source-sha` inside its single root step. Its own `exec` of the installer became a plain call so the write can follow it. `lib/updates.sh check_nightfall_source` reports `behind` when that file differs from the checkout's HEAD. When the file is missing, it reports `behind` with installed `(unrecorded)`, because a build installed by hand or before this change cannot be traced to a commit. The next successful `update nightfall` writes the file. `update nightfall`'s summary says "rebuilt from the checkout", because the pull step is a harmless no-op in this case.
- **The i915 refusal now exits 3 and prints `NF_I915_ENTRY=<options>`.** This is `lib/nightfall-cmdline-check.sh`'s "this boot carries no i915 options, but Nightfall's entry has ..." case. It previously exited 1 like every other refusal. `apply.sh` passes the code through unchanged. `update nightfall --nightfall-cmdline "<opts>"` keeps the options; `--nightfall-cmdline ""` drops them (set but empty counts as explicit, because the check tests `${NIGHTFALL_CMDLINE+x}`). The GUI catches exit 3 after an update and asks **Keep them / Drop them**. Bob hit this on the Slate: his normal boot is bare through a saved 7.2.8 cmdline override, so "reboot normally" was no way out. The Nightfall session was asked to treat a saved override as deliberate. **That refusal lives in this repo, not only in `install-nightfall.sh`**, so any such change has to land here too. Recovery and nomodeset refusals still exit 1, so the GUI offers no choice for them.
- **`cros-fp-fingerprint` now installs its own prerequisites.** It checks for `git`, `curl`, a C linker (`cc` → `build-essential`) and `dbus-send` (`dbus-bin`) and installs missing ones in one apt call *before* the Rust download. Without cargo, it downloads `rustup-init` from static.rust-lang.org, checks it against the published `.sha256`, and runs `-y --profile minimal --no-modify-path` as the user: no root, never `curl | sh`, removable with `rustup self uninstall`. A build check (`FIXER_BUILD_ONLY`) never downloads or installs and exits 2 instead. The whole install (binary, unit, systemd steps, suspend hook) is now one `$SUDO bash -s`, down from eight prompts. Applying this fix is still Bob's decision every time: it adds a root suspend hook and PAM changes.
- **GUI action windows show progress, not a scrolling log.** `_run_in_window` shows a pulsing bar and the latest output line. The full log sits under a collapsed **Details** section that opens on failure. It also takes `on_exit(rc, output)`, which is how the i915 choice is offered. ### Camera rotation: settled, do not re-add
`camera-follow-rotation` was removed on 2026-09-11. It republished the camera through `libcamerasrc -> videoflip -> v4l2loopback` so the image tracked the accelerometer; it never worked well enough to keep, and the problem is settled the other way instead — `display-autorotate` pins the screen to landscape while a camera app is open, so the image and the screen agree without a second video pipeline. Its two daemons (`chromebook-camera-rotate`, `chromebook-camera-nudge-pipewire`) went with it. BobZKernel patch 9205 (in-tree v4l2loopback) outlives it, serving Waydroid's external-camera HAL.

### Offline apply through Nightfall: considered, deliberately not built
Running risky fixer applies from inside Nightfall, with the real root not in use, was explored on 2026-09-14 and rejected. Worth knowing before re-proposing it:
- The three hard locks came from **streaming the camera**, never from applying a fix, so it would not have prevented them.
- Only four fixes could run offline at all (`ipu3-imgu-iommu`, `panel-brightness-dpcd`, `nightfall-default`, `audio-avs-dsp`, all `update-grub`/`update-initramfs`). The rest need a live systemd/udev/dbus, a user session, or a network the initramfs lacks.
- Its real value would have been **offline revert** of a boot-breaking command-line fix, and Nightfall already covers that: Edit hands back the whole command line, and "save it for this kernel on every boot" writes a whole-line override to `/boot/nightfall-cmdline` that survives `update-grub` and never touches `grub.cfg` or recovery entries. Both command-line fixes' `danger` text now points there.
- Mechanics, if it is ever revisited: `Fix.run()` overwrites `FIXER_SUDO`, so a runner must call scripts directly with `FIXER_SUDO=env` (empty does not work, `:-` falls back to `sudo`); Nightfall's install loop is bounded against boot loops; every write needs remount-rw with restore-ro in a trap.

## Non-obvious overlaps with BobZKernel / nightfall-boot-manager

1. **Volume buttons — two different bugs, don't conflate them.** `ec-buttons-poll` exists because "the EC never delivers MKBP events after boot — the interrupt fires once at startup and never again" (polls the EC FIFO via the synchronous command path instead). This is a **different failure mode** from BobZKernel's patch 9207 (GOOG0007's ACPI `_STA` misreporting absent after a coreboot firmware update, fixed via `override_status_ids[]` so `cros_ec_keyb` binds at all). `ec-buttons-poll`'s own detection adapts to either state at runtime (it asks whether `cros_ec_keyb` is bound, never which firmware is installed), so nothing here needed code changes when the facts below changed — only this note was stale.

   **As of MrChromebox firmware 2609 (coreboot 26.06-1248-g2332723df69), the ACPI `_STA` bug is fixed upstream in firmware, confirmed and settled** — `GOOG0007:00/status` reads `15`, `physical_node` exists, `cros-ec-keyb` binds, on a **generic** (non-BobZKernel) kernel with no 9207. **Patch 9207 is now confirmed obsolete and BobZKernel is dropping it** — this was an open question as of 2026-09-18; it no longer is. Do not assume every Slate is on 2609 regardless — the originally-cited MrChromebox 2606.1 bug this paragraph used to describe as "live on the stock kernel" is now specifically the **2606.1-and-earlier** case, not a permanent property of "stock".

   The **separate** delivery bug (interrupt-starvation: the EC's own IRQ fires once at boot and never again, independent of GOOG0007 enumeration) has a root cause and a fix in progress as of 2026-09-30: a 2022 downstream patch dropped the EC's own interrupt resource from CREC's `_CRS`. **SlateFirmware's patch 0001b restores it**, upstreaming to MrChromebox (MrChromebox/firmware#1004) — confirmed live on a Slate running MrChromebox-2609.0-1-gf2fbda7cf0: a stock/generic kernel there shows the EC's own interrupt (a second `chromeos-ec` line in `/proc/interrupts`, distinct from the FPMCU's single line) and needs neither 9201 nor `ec-buttons-poll`. `ec-buttons-poll`'s `detect.sh` and its daemon's own runtime check (`kernel_already_handles`) both now test for this directly (`lib/ec-buttons.sh irq-live`, and the daemon's own copy of that check, kept in sync) and stand down when it is present and `cros_ec_keyb` is bound — this matters beyond redundancy, because the poller injects its own synthetic key through a second uinput device, so running it alongside a working native path double-fires every press. Until 0001b lands everywhere, Slate volume buttons still need 9201 on BobZKernel or `ec-buttons-poll` on stock/generic without it. If volume buttons go silent again specifically **after long uptime** (not right after boot) on firmware predating 0001b, that's this interrupt-starvation problem, not the ACPI one.

2. Kernel patch **9201** (`cros-ec-poll-event-fifo-fallback.patch`, BobZKernel `pixel-slate` branch) is the in-tree version of the same idea as `ec-buttons-poll` — deliberately not offered here as a fixer fix, since this tool avoids requiring kernel rebuilds. Note a drain alone is only half the path: without 9207's enumeration fix it has no consumer.
3. **`panel-brightness-dpcd` is the same fix as Nightfall's blank-screen bug**, independently found from two directions. This fixer sets `i915.enable_dpcd_backlight=2` on the main kernel because "i915 picks a backlight control method the panel does not implement." The picker's bare GRUB entry (no cmdline at all) hit the identical root fact — DRM mode-set succeeds, screen stays dark — fixed in `install-nightfall.sh` by copying `i915.*` params live from `/proc/cmdline` (a more general version of what this fixer does explicitly). This fixer's own `lib/kernel-cmdline.sh` also copies `i915.*` options into Nightfall's entry, but **additions only**: a revert never strips one from it, so undoing a panel fix cannot darken the escape hatch, and `picker-drift` flags only Nightfall *lacking* an option the running kernel boots with, never carrying an extra one. Keeping it is **temporary by design**: `install-nightfall.sh` deletes and rewrites its whole entry from the running kernel's `/proc/cmdline` on every (re)install, and a normal boot that lit the panel is proof of that i915 set, so a reinstall is the correct moment for a kept option to go. Do not "fix" that with `NIGHTFALL_CMDLINE`. The real hole is reinstalling from a **recovery/nomodeset** boot, whose command line carries no i915 options and would write an empty set, leaving Nightfall dark; `lib/nightfall-cmdline-check.sh` refuses that before the build. `sudo`/`pkexec` scrub the environment, so the fixer passes a user-set `NIGHTFALL_CMDLINE` to the installer explicitly.
4. `ipu3-imgu-iommu` / kernel patch 9204 is the same IOMMU identity-domain requirement (PCI `8086:1919`) as documented for pixel-slate camera work — cross-referenced, not duplicated.
5. `accelerometer-orientation`/`display-autorotate`/`tablet-mode-switch` were **prior art** for Nightfall's auto-rotate, which is now **done and calibrated** (`7d69a4b`, plus `5a7bc5e` for touch that still followed the startup rotation). The driver chain question that blocked it is answered and needs no re-checking: `cros-ec-accel` and `cros-ec-gyro` enumerate as IIO devices inside the stripped `picker-kernel` too, visible in every Nightfall boot log under "display accelerometer" — `chromebook-fixer logs nightfall`. That block exists *because* the calibration work used it, so do not read it as an open question. This repo's own rotation fixes are unaffected: they handle the full OS, Nightfall handles its own environment, and neither drives the other.
